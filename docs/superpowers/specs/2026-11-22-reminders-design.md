# 알림 추천(재구매·접종·일정) 설계

작성일 2026-11-22 · 상태: 설계 초안 3판(법적 유의사항·발송 횟수·알림 이력·보호자 수신 동의 표시 반영, 사용자 승인 전) · 앞선 작업: `docs/superpowers/plans/2026-11-22-messaging-qr.md`(메시지 발송 QR, 완료)

## 1. 무엇을, 왜
사장님(관리자 1명)이 "이 보호자에게 슬슬 알림을 보낼 때가 됐다"를 기억에 의존하지 않도록, ERP가 판매·진료·일정 기록을 보고 **대시보드에 먼저 알려 주고**, 사장님이 [알림 보내기]를 누르면 이미 만들어 둔 **메시지 발송(QR) 화면에 문구가 채워진 채로 열리게** 한다. 사장님이 한 말: 판매 기록의 구매 패턴을 보고 재구매가 가까우면 "알림 보내겠습니까?"를 물어보고, 일정(공유 업무)에도 반려동물·보호자를 연결하고, 진료·날짜 데이터를 기준으로 삼으며, 이 정보는 **대시보드의 중요한 정보**여야 한다.

## 2. 목표 / 하지 않을 것 / 실패로 보는 것
**목표**
- 대시보드에 "알림 보낼 때예요" 카드: 지난 것·오늘·이번 주 예정 건을 반려동물 이름·무엇·마지막 날짜·다음 예정일·남은 기간과 함께 보여 준다.
- 카드의 [알림 보내기] → 메시지 발송 화면이 반려동물·문구·날짜가 채워진 채로 열린다. 사장님은 폰으로 QR을 비추고 전송만 누른다.
- 보낸 건은 "보냄"으로 표시해 같은 알림이 반복해서 뜨지 않게 한다. 보내지 않을 건은 "넘김"으로 치울 수 있다.
- 입력은 최소화: 분류별 주기 6칸 + 예외 상품만 + 접종 판매 때 버튼 한 번.

**하지 않을 것**
- 자동 발송(서버·문자 업체·알림톡) 없음. 전송은 항상 사장님이 폰에서 누른다.
- 구매 패턴 자동 학습(주기를 과거 간격에서 추정)은 이번 범위가 아니다. 나중에 정확도를 높이는 용도로 남겨 둔다.
- 엑셀 과거 매출(`sales_legacy`)은 반려동물 연결이 없어 개별 알림 대상으로 쓰지 않는다.
- 직원(staff) 계정에는 보이지 않는다(메시지 발송과 같은 관리자 전용).

**실패로 보는 것(기술적으로 동작해도)**
- 틀린 반려동물·틀린 날짜로 알림이 추천되거나 문구에 들어가는 것.
- 입력 칸이 많아져 어르신이 쓰기 어려워지는 것.
- 같은 알림이 보낸 뒤에도 계속 뜨거나, 보냈는지 안 보냈는지 알 수 없어 같은 보호자에게 두 번 보내는 것.
- 예정일이 지난 뒤에도 재촉하거나, 광고로 볼 수 있는 문자를 요건 없이 보내는 것(§12, §13).
- 보호자 연락처·이름이 직원 권한 밖으로 노출되는 것.

## 3. 현재 상태(확인한 사실)
- 공유 업무(`action_tasks`): 제목·설명·상태·우선순위·날짜·시간만 있고 반려동물·보호자 연결이 없다. 일정 등록(admin 전용 insert)은 업무 폼(`#newTaskForm`)으로 한다. 수정 권한은 열 단위로 제한되어 있다(`title, description, status, priority, due_date`).
- 판매: `sale_items`에 `pet_id`가 있어(13번 SQL) 반려동물을 고른 판매는 "누가 언제 무엇을 샀는지"가 정확하다. 상품은 분류(`product_categories.group_name`: drug·feed·supplement·supply·vaccine·service)에 속한다. 접종 상품 판매는 `vaccinations`(`pet_id` 포함)에도 남는다.
- 진료 기록(`pet_visits`): 날짜별 자유 글. 접종 내용은 글자(키워드 `isVaccineText`)로만 알 수 있다.
- **"다음 접종일/재구매일"은 어디에도 저장되지 않는다.**
- 기존 쓰기 방식: 쓰기는 SECURITY DEFINER RPC(`rpc_*`)로, 읽기는 `is_staff()` RLS로 한다. 설정 성격의 쓰기는 `is_admin()`.
- 기존 대시보드: 오늘 일정 패널(`#todaySchedulePanel`), 매출 요약 카드, 추이 차트. 메시지 발송 화면은 `app.js`의 `msg*` 구역이며 `MessagingCore`(문구·번호·날짜 순수 함수)와 `QrCode`를 쓴다.

## 4. 결정한 것(사용자가 정함)
1. 공유 업무에 반려동물(보호자 포함) 정보를 DB에 추가한다.
2. 판매 기록의 구매 패턴을 보고 재구매가 가까워지면 "알림 보내겠습니까?"를 묻는다.
3. 주기 입력은 **A+B 방식**: (A) 약(상품)별·분류별 기본 주기를 "판매 단위 1개당 며칠분"으로 입력하고, (B) 판매할 때 수량에 맞춰 계산된 다음 알림일이 **미리 채워져** 나타나며 약사 사장님이 상황에 따라 고치면 **그 값이 우선**한다(접종은 "3주 후/4주 후/1년 후" 버튼). 같은 약이라도 몇 개를 사갔느냐에 따라 주기가 달라지기 때문이다(사용자 지적, 2026-11-22).
4. 진료·판매 기록의 날짜를 기준으로 한다.
5. 정보는 대시보드에 표현한다.
6. 표현: 마지막 날짜 → 다음 예정일과 남은 기간을 함께 보인다("3일 뒤"·"오늘"·"내일"). 목록에는 **예정일 7일 전부터** 올린다(분류별로 바꿀 수 있게 주기와 같은 칸에서 정한다). **예정일이 지난 뒤의 처리는 §13이 정한다**(재구매는 지나면 목록에서 뺀다 — 다른 곳에서 샀거나 방문 의사가 없을 수 있다는 사장님 의견).
7. 알림을 보냈는지 알 수 있는 **알림 이력**을 메시지 발송 화면 아래쪽에 두고, 다시 보내는 일이 없게 한다(§14).

## 5. 접근 방식(검토한 것)
- **① 읽기 전용 DB 함수 하나가 후보를 계산하고 화면은 그대로 보여 준다(채택).** 판매·일정·접종 기록과 주기 설정을 `rpc_reminder_candidates()`가 합쳐 돌려준다. 장점: 계산이 한 곳, 화면 코드가 단순, 권한(관리자만)을 DB에서 지킨다. 단점: DB 함수 추가가 필요하다(승인 필요).
- ② 브라우저가 판매·일정 테이블을 전부 받아 `app.js`에서 계산한다. DB 변경은 줄지만 판매 건수가 늘면 느려지고, 규칙이 화면 코드에 흩어진다.
- ③ 서버 작업(스케줄러)이 미리 후보를 만들어 저장한다. 서버가 없는 현재 구조에 맞지 않고 비용·운영이 늘어 제외.
- 주기 입력 대안: C(과거 기록에서 자동 학습)는 과거 매출에 반려동물이 없고 진료 기록이 글이라 데이터가 부족해 보류. A+B를 사용자가 선택했다.

## 6. 설계(빌더가 이어서 계획할 수 있는 수준의 윤곽)
### 6.1 데이터(모두 추가만 한다. 기존 열·정책은 바꾸지 않는다 — **모두 사용자 승인 필요**)
- `action_tasks.pet_id bigint null references pets(id) on delete set null` + 인덱스. 업무 등록 때 선택(선택 항목). 기존 업무는 비어 있다. 보호자는 `pets.owner_id`로 따라간다(별도 열 없음). 수정 열 권한은 기존 그대로.
- `reminder_rules`: 주기 설정. 키는 분류(`group_name`) 또는 상품(`product_id`)(둘 중 하나), `interval_days`(**판매 단위 1개당 며칠분**, 예: 심장사상충약 1개=30일, 6개입 한 박스로 파는 약이면 한 박스=180일), `scale_by_quantity`(수량을 곱할지: 약·사료·영양제는 true, 접종처럼 한 번에 정해진 간격이면 false), `lead_days`(며칠 전부터 목록에 올릴지, 기본 7). 상품 설정이 분류 설정보다 우선. 설정이 없는 분류·상품은 알림 대상이 아니다(기본값을 임의로 넣지 않는다 — 의료 주기를 시스템이 정해 주지 않음). 읽기 `is_staff()`, 쓰기 관리자 전용 RPC.
- `pet_next_due`(반려동물+상품별 다음 날짜): 판매 시점에 **계산해서 저장한 다음 알림일**. `(pet_id, product_id, due_on, set_on, source 'auto'|'manual')` 한 쌍당 한 행(없으면 만들고 있으면 갱신). 판매 화면이 보여 준 값을 그대로 저장한다 — 자동 계산이면 `auto`, 약사 사장님이 고쳤으면 `manual`(고친 값이 곧 저장되는 값이라 **입력한 값이 항상 우선**). 판매 등록 RPC(`rpc_create_sale`)는 건드리지 않고, 판매 성공 뒤 별도 RPC `rpc_set_next_due(p_pet_id, p_product_id, p_due_on, p_source)`를 호출한다(두 단계라 둘째가 실패해도 판매는 정상이고, 후보 계산은 아래 대체 계산으로 대신한다). 판매 당시의 값을 저장해 두므로 나중에 주기 설정을 바꿔도 이미 판 건의 알림일은 바뀌지 않는다.
- `reminder_log`: 발송 이력(§14). `(id, pet_id, kind 'vaccine'|'rebuy'|'task'|'manual', ref_key, due_on null, status 'sent'|'skip'|'void', message_text, created_at, created_by)`. 같은 (반려동물, 종류, 기준, 예정일)에 `sent`/`skip`이 있으면 후보에서 제외, `void`(되돌림)이면 후보로 돌아온다. 보낸 문구 사본(`message_text`)을 남긴다. 연락처는 저장하지 않는다.
- `owner_reminder_pref`: **보호자별 안내 수신 상태**(수신거부 표시와 동의 표시를 하나로 합침). `(owner_id primary key references owners(id) on delete cascade, status 'consented'|'optout', status_on date, method text null (예: '구두'·'서면'), note text null, updated_at, updated_by)`. 행이 없으면 "미확인". `optout`이 `consented`보다 우선하며, 거부한 보호자는 모든 후보에서 제외한다. 동의를 받은 보호자는 재구매 안내의 6개월 한도가 풀린다(§12). 읽기 `is_admin()`, 쓰기는 관리자 전용 RPC `rpc_set_reminder_pref(p_owner_id, p_status, p_method, p_note)`(상태를 없애는 `null`도 허용).

### 6.2 후보 계산(`rpc_reminder_candidates(p_today date)`, 읽기 전용, `is_admin()`만)
각 후보는 `{pet_id, pet_name, owner_name, kind('rebuy'|'vaccine'|'task'), item_label, last_on, due_on, days_left, ref_key}`.
- **재구매/접종(판매 기반):** 반려동물이 선택된 `sale_items`에서 (반려동물, 상품)별 가장 최근 구매일을 구하고, `due_on` = 그 반려동물·상품의 `pet_next_due`가 있으면 그 날짜(§11의 "최근 구매보다 이른 저장값은 무시" 규칙 적용), 없으면(옛 판매·두 번째 단계 실패) **대체 계산**: 최근 구매일 + (규칙이 `scale_by_quantity`이면 `interval_days × 그 구매의 수량`, 아니면 `interval_days`). `due_on - lead_days <= 오늘`이면 후보. 규칙도 `pet_next_due`도 없으면 후보가 아니다. 분류가 접종이면 `kind='vaccine'`.
- **진료 기록 기반 보조:** 판매 기록이 없는 반려동물은 `pet_visits`에서 접종으로 보이는 가장 최근 방문일(키워드)에 **접종 분류 규칙의 주기**를 더해 후보로 만든다(상품을 모르므로 항목 이름은 "접종"). 같은 반려동물의 판매 기반 접종 후보가 있으면 그쪽이 우선(중복 금지).
- **일정(공유 업무) 기반:** `pet_id`가 있고 상태가 완료가 아닌 `action_tasks` 중 `due_date`가 오늘~7일 뒤인 건. `kind='task'`, 일정 시간이 있으면 함께 보인다.
- **판매 기반에서 제외:** 취소된 판매(`sales.status = 'cancelled'`)는 마지막 구매일 계산에서 뺀다(취소 시 `vaccinations` 행도 이미 지워진다). 보호자(`pets.owner_id`)는 필수라 보호자 없는 반려동물은 없다. 보호자 연락처가 비어 있어도 후보는 보이고, 메시지 발송 화면에서 번호를 직접 입력하게 한다.
- 정렬: 오늘 → 가까운 날짜 순(접종 유예 건은 맨 위). `reminder_log`에 같은 키가 있으면 제외. 예정일이 지난 건의 처리·노출 창·횟수는 §13을 따른다.

### 6.3 화면
- **대시보드 "알림 보낼 때예요" 카드**(관리자만): 제목 옆에 오늘 N건·이번 주 M건, 오늘 보낸 건수. 각 줄 `반려동물 · 무엇 · 마지막 날짜 → 다음 예정일 · 남은 기간 · [알림 보내기] [넘김]`. 비어 있으면 "지금 알릴 건이 없어요", 주기 설정이 하나도 없으면 "알림 주기를 정하면 여기에 알림이 나타나요 [주기 정하러 가기]". 기존 화면 위쪽(오늘 일정 근처)에 둔다.
- **[알림 보내기]**: 메시지 발송 화면으로 이동하며 반려동물·종류(접종 안내 또는 예약 확인 또는 재구매 안내)·날짜를 채운다. 문구는 기존 `MessagingCore.buildMessageText` 템플릿을 쓰고 재구매용 템플릿 하나를 추가한다. 사장님이 폰에서 전송한 뒤 돌아와 **[보냈어요]**를 눌러 `reminder_log`에 'sent'를 남긴다(QR만으로는 전송 여부를 알 수 없다).
- **알림 주기 설정**: 메시지 발송 화면 하단 또는 별도 접이식 구역(관리자). 상단에 분류 6줄(`분류 이름 · 며칠마다 [ ] · 며칠 전부터 알림 [7]`), 아래 "예외 상품" 접이식에서 상품을 초성 검색 카드로 골라 같은 두 칸을 입력. 문구는 쉬운 말(`며칠마다 다시 필요해요`).
- **판매 관리 화면(B)**: 반려동물이 선택되고 **주기 설정이 있는 상품**이 목록에 담기면 그 줄에 계산된 다음 알림일이 미리 채워져 보인다. 예: `심장사상충약 3개 → 다음 알림일 2027-02-20 (3개 × 30일) [날짜 고치기]`. 평소에는 아무것도 누르지 않아도 되고, 수량을 바꾸면 자동으로 다시 계산되며(직접 고친 날짜는 유지), 약사 사장님이 [날짜 고치기]로 바꾸면 그 값이 저장된다. 접종 상품(수량을 곱하지 않는 설정)은 날짜 대신 "다음 접종: 3주 후 / 4주 후 / 1년 후 / 안 정함" 버튼 줄을 보인다(기본 안 정함). 주기 설정이 없는 상품은 아무것도 보이지 않는다. 판매는 어떤 경우에도 막지 않는다. 판매 성공 후 `rpc_set_next_due`를 호출한다.
- **업무(일정) 등록 폼**: 반려동물 선택 칸 추가(선택, 판매 관리와 같은 초성 검색 카드). 업무 상세에 연결된 반려동물이 있으면 "알림 보내기" 버튼을 보인다.

### 6.4 권한·프라이버시
- 후보 함수·주기 쓰기·발송 기록 쓰기는 관리자만. 보호자 연락처는 후보 목록에 싣지 않고 메시지 발송 화면이 기존 방식(`rpc_get_pet_detail`)으로 따로 읽는다.
- 화면 로그·테스트 로그에 이름·번호를 남기지 않는다. 모든 DB 변경은 마이그레이션 SQL 파일(`db/22_...sql`)로 남기고 승인 전에는 실행하지 않는다.

## 7. 제약
- 순수 HTML/CSS/JS, 새 라이브러리·서버 없음. 기존 판매 등록·재고·로그인·공유 업무·메시지 발송 동작은 그대로 유지한다.
- 장년층 사용자: 타이핑 최소(초성 카드 검색, 버튼 선택), 쉬운 말, 큰 버튼. 개발 용어(RLS, RPC 등) 화면 노출 금지.
- DB 변경은 추가만. 승인 없이 SQL 실행·배포·push 하지 않는다.
- 데스크톱·태블릿·모바일에서 가로 넘침 없음.

## 11. 검토 후 보완(2026-11-22, 독립 검토자 질문에 대한 답 — 모두 내가 정한 것)
1. **다음 날짜(B)와 새 구매가 어긋날 때:** 가장 최근 구매가 이긴다. `pet_next_due`에는 저장한 날(`set_on`)을 함께 두고, 그 날짜가 마지막 구매일보다 이르면(= 새로 구매했는데 버튼을 안 누른 경우) 무시하고 분류·상품 주기(A)로 계산한다. 같은 반려동물·상품을 다시 팔면서 "안 정함"이면 옛 날짜가 남아 오래된 알림으로 계속 뜨는 일이 없다.
2. **발송 기록 `ref_key`와 "넘김":** `ref_key`는 종류별로 `상품 id`(판매 기반), `'visit'`(진료 기록 기반), `업무 id`(일정)로 둔다. 키에 예정일(`due_on`)이 들어가므로 "보냄/넘김"은 **그 예정일의 알림만** 숨긴다. 새 구매·새 날짜로 예정일이 바뀌거나 업무의 날짜를 고치면 다시 후보로 올라온다. 보낸 뒤 구매가 없으면 그 예정일의 알림은 다시 뜨지 않는다(반복해서 재촉하지 않는다).
3. **진료 기록 보조 규칙(조심스럽게):** 판매로 접종 후보가 이미 있는 반려동물(어떤 접종 상품이든)은 쓰지 않는다. 쓸 때는 방문 글에 `백신` 또는 `접종`이 있고 `예정`·`예약`·`다음`이 **없는** 가장 최근 방문만 쓴다(구충제 상품명 등은 쓰지 않는다). 항목 이름에 "접종 (진료 기록에서 찾음)"이라고 출처를 보여 사장님이 보고 판단한다. SQL에는 이 키워드 목록을 따로 정의한다(앱의 JavaScript 목록을 서버에서 쓸 수 없다).
4. **메시지 발송 화면 채우기:** 지금 화면은 밖에서 채우는 입구가 없다. 4단계에서 `msg*` 구역에 `msgOpenWith({ petId, type, dueDate, vaccineName })` 하나를 추가해 대시보드가 부른다(반려동물 선택·종류·날짜·접종 이름을 채우고 같은 화면 로직으로 문구와 QR을 만든다). 일정 후보는 `예약 확인`, 접종 종류는 `접종 안내`, 그 외 재구매는 새 `재구매 안내` 문구를 쓴다. 이 추가는 기존 동작을 바꾸지 않는다.
5. **카드의 "마지막 날짜":** 판매 기반은 그 반려동물·상품의 마지막 구매일, 진료 기록 기반은 방문일, 일정은 "마지막" 대신 일정 날짜(·시간)를 보인다.
6. **"오늘"의 기준:** 한국 시간(`Asia/Seoul`) 날짜. 함수는 날짜를 인자로 받지 않고 DB에서 한국 날짜를 계산한다(7일 전 경계가 화면과 어긋나지 않게).

## 12. 법적·규정 유의사항(조사 결과, 2026-11-22 — 법률 자문 아님, 원문 확인 필요)
확인한 근거는 정보통신망법 제50조·시행령 제61조 해설, 법제처 유권해석, 개인정보보호위원회 자료, 수의사법 관련 기사다. 현행 조문 전체와 예약·진료 안내 직접 사례는 확인하지 못했다.
1. **정보성 vs 광고성.** 접종 일정·예약 확인·진료 후 안내는 진료·거래 관계에서 이행에 필요한 안내라 광고성이 아니라는 해석이 일반적이다. **재구매 안내(약·사료·영양제를 다시 사라는 알림)는 구매 권유라 광고성으로 볼 소지가 있다.** 광고성 판단은 문구와 목적에 따라 달라지므로 안내 내용만 담고 병원 홍보·할인 문구를 섞지 않는다.
2. **광고성이면.** 원칙은 사전 동의. 예외: 거래를 통해 연락처를 직접 받은 사업자가 **거래 종료일부터 6개월 이내**에 보내는 경우(시행령 제61조, 법제처 해석상 거래 기간은 6개월에 포함하지 않는다). 그리고 (광고) 표기(소괄호), 전송자 명칭·연락처, 수신거부 방법 안내, **오후 9시~오전 8시 전송 별도 동의**, 수신거부 의사를 밝힌 사람에게 같은 내용 재전송 금지. 위반 시 3천만 원 이하 과태료. 개인 휴대폰으로 보내는 문자도 같다.
3. **개인정보보호법.** 진료·예약을 위해 받은 연락처를 그 목적 밖(마케팅)에 쓰려면 별도 동의가 필요하다. 접종·예약 안내는 진료 연장선이라 목적 범위 안으로 보는 것이 자연스럽지만 확정은 아니다. 병원 접수 동의서에 "진료·안내 연락" 문구가 **있다고 사용자가 확인했다**(2026-11-22). 이는 개인정보 이용 동의이고, **광고성 정보 수신 동의와는 별개**다(재구매 안내는 §16의 수신 동의 표시로 다룬다).
4. **수의사법.** 다른 동물병원을 이용하려는 소유자를 자기 병원으로 유인하는 행위는 금지(시행령 제20조의2 관련 논란). 이 기능은 **자기 병원의 기존 고객**만 대상으로 하고, 할인·혜택 문구와 "전문의", "최고" 같은 과장 표현을 쓰지 않는다. 동물용의약품(전문의약품) 광고 제한은 확인하지 못했다 — 재구매 대상 약품 문구는 이름·시기 안내에 그친다.
5. **음성 입력([말하기]).** 크롬은 음성을 구글 서버로 보내 글자로 바꾼다. 보호자 이름·번호는 말하지 않도록 이미 안내한다.
6. **개인정보 노출·보관.** 알림·이력은 관리자 전용이고 보호자 이름·반려동물 이름·보낸 문구만 보인다(연락처는 이력에 저장·표시하지 않음). 로그에 이름·번호를 남기지 않는다. 이력 보관 기간은 필요한 만큼만 두고 오래된 이력은 정리할 수 있게 한다(구체 기간은 사용자 결정).

**설계에 넣는 장치**
- 분류를 둘로 나눈다. `vaccine`(접종)은 **정보성 안내**, `drug`·`feed`·`supplement`·`supply`·`service`는 **재구매 안내(광고성 소지)**.
- 재구매 후보는 **마지막 구매일(거래 종료일 대용)로부터 6개월 이내**인 건만 올린다. 6개월을 넘으면 후보에서 뺀다. **단, 그 보호자가 안내 수신에 동의한 상태(`consented`)이면 6개월 한도 없이 올린다**(예정일 지난 건은 §13대로 제외). 동의가 있어도 (광고) 표기·수신거부 안내·야간 금지는 그대로 지킨다.
- 재구매 후보에서 [알림 보내기]를 누르면 메시지 발송 화면이 문구 앞에 `(광고)`를 붙이고 끝에 수신거부 안내 문구를 넣고, 현재 시각이 오후 9시~오전 8시이면 "밤에는 보낼 수 없어요(광고)"를 보여 QR을 만들지 않는다. 수신거부 안내의 정확한 문구·방법(무료 수신거부 수단 필요 여부)은 **사용자가 법적 확인 후 확정**하는 상수로 두고, 확정 전 기본값은 "수신거부: 병원에 말씀해 주세요"로 한다(제 초안).
- 재구매 안내는 **주기 설정에서 값을 넣어야만** 동작한다(기본 꺼짐). 주기 설정 화면의 재구매 분류 옆에 "광고로 볼 수 있어요. 보내기 전에 확인하세요" 안내를 둔다.
- **보호자 수신 상태(`owner_reminder_pref`, §16)**: 거부(`optout`)한 보호자는 모든 후보에서 제외하고, 메시지 화면에서 그 보호자를 고르면 "문자를 원하지 않는 분이에요" 경고(수동으로 보내는 것도 막지는 않되 눈에 띄게 경고). 동의(`consented`)한 보호자는 재구매 안내의 6개월 한도가 풀리고 "안내 받기로 한 분" 배지가 붙는다.

## 13. 발송 횟수·시기 정책(제안 — 내가 정함, 사용자가 고칠 수 있음)
원칙: **한 건(반려동물 + 무엇 + 예정일)당 최대 1회**, 예정일 앞의 정해진 창 안에서만, 예정일이 지나면 재촉하지 않는다. 같은 문자를 여러 번 받으면 싫어하고 신고·차단으로 이어질 수 있기 때문이다.
| 종류 | 목록에 올리는 시기 | 횟수 | 예정일이 지나면 |
|---|---|---|---|
| 접종 안내(정보성) | 예정일 7일 전부터 | 1회 | 한 번도 안 보냈으면 **예정일 +7일까지만** "지났어요"로 남기고(건강 관련이라 놓침을 한 번 구제), 이후 제외. 이미 보냈으면 바로 제외 |
| 예약 확인(일정) | 예약일 3일 전부터, 전날 보내기를 권장 | 1회 | 예약일이 지나면 제외 |
| 진료 후 안내 | 추천 목록에 올리지 않음(사장님이 필요할 때 메시지 화면에서 직접) | — | — |
| 재구매 안내(광고성 소지) | 예정일 7일 전부터(분류별로 고침) | 1회 | **즉시 제외.** 다른 곳에서 샀거나 방문 의사가 없을 수 있다 |
보호자·반려동물 단위 보호 장치
- **중복 방지(같은 건일 때만):** `reminder_log`에 `sent`/`skip`이 있으면 같은 건(반려동물 + 종류 + 예정일)은 후보에서 다시 뜨지 않는다. 메시지 화면의 "이미 보냈어요" 안내도 **같은 건일 때만** 보인다 — 같은 반려동물·같은 종류이고 **같은 예정일**(접종·예약처럼 날짜가 있는 종류). 날짜가 없는 종류(진료 후 안내·직접 쓴 문구)는 **오늘 이미 보낸 경우에만** 안내한다. 주기가 짧은 약(월 1회)이나 2~3주 간격 접종은 예정일이 달라 매번 새 건이므로 "이미 보냈어요"가 뜨지 않는다(고정 기간 30일 방식은 쓰지 않는다 — 사용자 지적 2026-11-22). 안내는 막지 않고, "그래도 보낼 수 있어요"로 알리기만 한다.
- **같은 보호자에게 대기 건이 둘 이상**이면 카드에 "같은 보호자 2건" 배지로 알려 문자를 두 통 보내지 않게 한다(문구를 합치는 기능은 이번 범위 밖).
- **재구매는 같은 보호자에게 14일 안에 이미 보냈다면** 카드에 "최근에 안내했어요" 배지를 붙인다.
- **수신거부(`optout`) 보호자는 제외**(§12, §16).
- 접종 +7일 유예와 재구매 6개월 한도, 7일 전 창은 분류별 설정 칸에서 고칠 수 있게 한다.

## 14. 알림 이력 화면(메시지 발송 화면 아래쪽)
목적: 보냈는지 아닌지 애매한 것을 없애고 같은 알림을 다시 보내지 않는다. 읽기 쉽게, 큰 글씨, 상태는 색 배지.
- **기록 방법:** QR은 전송 여부를 알 수 없으므로 QR 아래에 큰 **[폰에서 보냈어요]** 버튼을 둔다. 누르면 `sent`로 기록(보낸 문구 사본 포함). 보내지 않고 다른 반려동물을 고르거나 화면을 떠나려 하면 "방금 만든 문자를 보냈나요? [보냈어요] [안 보냈어요]"를 한 번 묻는다. 추천 카드의 [넘김]은 `skip`, 잘못 누른 기록의 [되돌리기]는 `void`로 바꿔 후보로 돌려보낸다. **추천에서 온 것이든 수동으로 만든 것이든 모든 문자를 같은 이력에 남긴다**(`kind='manual'` 포함).
- **조회:** "보낸 알림 이력" 구역 — 기간 버튼(오늘 / 7일 / 30일 / 전체, 기본 30일), 상태 버튼(전체 / 보냄 / 넘김), 반려동물·보호자 초성 검색.
- **한 줄 구성(카드형, 좁은 화면에서도 안 잘림):** `날짜·시각` · `반려동물 (보호자)` · `종류 배지(접종/예약/재구매/직접)` · `예정일` · `상태 배지(보냄 초록·넘김 회색·되돌림 흐림)` · `[문구 보기]`(누르면 보낸 문구 전체가 펼쳐짐) · `[되돌리기]`. 최신순, 날짜가 바뀌는 곳마다 날짜 머리글.
- **빈 상태:** "아직 보낸 알림이 없어요".
- **개인정보:** 연락처는 보이지 않는다. 이력은 관리자만 본다.
- **수신 상태 관리:** 이력 구역 옆의 작은 목록에서 동의·거부 보호자를 보고 고치거나 지울 수 있다(§16).

## 15. 이번 판에서 내가 정한 것
- §12의 분류 나눔(접종=정보성, 그 외=재구매 안내), 6개월 한도, (광고) 표기·수신거부 문구 기본값, 야간 차단, 재구매 기본 꺼짐.
- §13의 횟수·창·유예(접종 +7일, 재구매 즉시 제외), 14일 안내 배지, 같은 보호자 배지.
- 이력 화면은 메시지 발송 화면 하단, 가장 먼저 만드는 0단계. 이력 보관 기간과 수신거부 문구 확정은 **사용자 결정**.
- DB 변경 적용 순서는 사용자 답이 없어 **단계마다 SQL을 보여 드리고 승인받아 적용·확인하는 방식**으로 가정한다(바꾸려면 알려 주세요).
- 서브에이전트 없이 직접 조사·정리했다(조사·문서 중심이고 서로 이어진 작업이라 조율 비용이 더 컸다).

## 16. 보호자 안내 수신 상태와 동의 체크박스(사용자 결정, 2026-11-22)
재구매 안내(광고성 소지)를 받겠다고 한 보호자를 ERP에 표시해 두는 장치. 지금까지 없었고, 사용자가 판매 입력 화면에 체크박스를 두는 방식에 동의했다.
- **단위는 판매 건이 아니라 보호자.** 판매마다 체크하면 동의가 여러 번 쌓여 최신·철회 관리가 어렵다. 한 보호자에 한 상태(`owner_reminder_pref`).
- **판매 관리 화면:** 반려동물을 고르면 그 보호자의 현재 상태가 보인다. 체크박스 "복용 시기 안내 문자를 받기로 했어요"(+동의한 날짜). 체크하면 `consented`를 기록(날짜=오늘, 방법="구두"가 기본값이고 "서면"으로 바꿀 수 있다), 체크를 해제하면 상태를 지운다. 반려동물을 고르지 않은 판매에서는 비활성. 같은 보호자의 다음 판매에서는 이미 체크되어 보인다.
- **거부(`optout`)**: 보호자가 "문자 그만 보내세요"라고 하면 메시지 화면의 보호자 상태에서 [안내 안 받음]을 눌러 기록. 거부는 동의보다 우선하고, 체크박스를 다시 체크해도 거부를 풀려면 한 번 더 확인한다.
- **동의의 효과:** 재구매 후보의 6개월 한도 해제(§12). 접종·예약 안내는 정보성이라 동의 여부와 무관하게 가능하지만, 거부한 보호자에게는 보내지 않는다(경고).
- **증빙의 한계:** 사장님이 구두로 묻고 체크하는 방식은 동의했다는 증거가 약하다(분쟁 시 입증 책임은 병원 쪽). 접수 때 서명·체크를 받는 동의서가 있으면 "서면"으로 기록하고 원본을 따로 보관하길 권한다. 광고성 수신 동의는 일정 주기(2년으로 기억)마다 재확인해야 한다는 규정이 있는 것으로 기억하지만 **확인하지 못했다** — 법적 확인 후 "확인한 지 오래된 동의" 표시를 추가할지 정한다.
- **개인정보:** 상태·날짜·방법·메모만 저장하고 연락처는 저장하지 않는다. 관리자만 읽고 쓴다.

## 17. 이번 판에서 내가 정한 것(추가)
- 수신거부 표시와 동의 표시를 하나의 보호자 단위 테이블(`owner_reminder_pref`)로 합쳤다. 동의 체크박스는 3단계(판매 화면 보강)에 두고, 수신 상태 읽기·고치기는 0단계의 메시지 발송 화면에 먼저 둔다.
- 동의의 기본 방법은 "구두", 거부가 동의보다 우선, 동의 해제는 상태 삭제.
- 2년 주기 재확인은 법적 확인 전까지 구현하지 않는다(문서에 남겨 둠).

## 18. 수량 반영 주기와 약사 입력 우선(사용자 결정, 2026-11-22)
- **단위:** `interval_days`는 **판매 단위 1개당 며칠분**이다. 3개를 사면 3 × 1개당 일수(`scale_by_quantity`가 true인 상품). 6개입 한 박스처럼 한 번에 여러 회분을 파는 상품은 그 판매 단위 기준으로 값을 넣는다.
- **우선순위(최종 알림일):** ① 약사 사장님이 판매 때 고친 값(`manual`) → ② 판매 화면이 자동 계산해 저장한 값(`auto`) → ③ 저장값이 없을 때의 대체 계산(최근 구매 + 주기 × 수량). §11의 "새 구매가 이긴다" 규칙은 그대로 적용한다.
- **입력 부담:** 자동 계산값이 미리 채워지므로 평소 추가 입력은 없다. 체중에 따른 용량 차이 등 예외일 때만 [날짜 고치기].
- **알아둘 점:** 일찍 더 사서 구매가 겹치면 다음 알림이 이르게 뜰 수 있다(목록에서 [넘김]으로 처리). 반려동물을 선택하지 않은 판매는 알림일이 저장되지 않는다.
- **새로 정한 것(내가 정함):** 수량이 같은 구매 줄에 여러 번 나뉘어 들어가면 `rpc_create_sale`이 (상품, 반려동물)별로 수량을 합치므로 합친 수량으로 계산한다. 주기를 입력하는 화면에는 상품마다 "1개당 며칠분"으로 보이게 하고 "판매 단위 1개"라는 뜻을 안내 문구에 적는다.

## 19. 알림 이력 개편과 문의 전화번호(사용자 요청, 2026-11-22 — 0단계 사용 후 피드백)
- **이력 보기:** 날짜별(그날 건수 표시)과 **보호자·반려동물별**(보호자마다 한 묶음: 반려동물별 건수·보낸 건수·마지막 날짜, 펼치면 문자들) 두 가지로 본다. 맨 위에 "오늘 N건 · 이번 달 M건 · 지금까지 보호자 K명에게 보냈어요" 요약을 둔다.
- **상태 이름을 쉬운 말로:** `sent`=보냈어요, `void`=되돌림, `skip`=건너뜀. 상태 보기는 "보낸 문자(기본)"와 "되돌린 것까지" 두 가지만 둔다. `skip`(넘김)은 4단계 추천 카드의 [넘김]에서만 생기므로 4단계에서 보기에 추가한다. 화면에 용어 설명 한 줄을 둔다.
- **문의 전화번호:** 문구 끝의 "문의: 전화번호"는 **기본으로 넣고**(사용자 결정), "문구 끝에 문의 전화번호도 넣기" 스위치로 뺄 수 있다. 끈 상태는 이 컴퓨터에 기억한다. 받는 분께 표시되는 **보내는 번호**(문자 앱에서 보내면 폰의 번호)는 이 방식으로는 바꿀 수 없다 — 병원 번호로 표시하려면 발송 업체의 발신번호 등록이 필요하다(§20).

## 20. 보류: 병원 번호로 문자 보내기(발송 업체 연동) — 2026-11-22
받는 분께 병원 번호가 **발신번호**로 표시되게 하는 개발은 보류했다. 사용자는 우선 QR 방식(폰 번호가 표시되고 문구 끝 "문의 전화"로 병원 번호를 알림)을 쓴다. 나중에 진행할 때의 출발점·준비물·연결 지점·비용·유의사항은 `docs/future-hospital-sender-number.md`에 모아 두었다. 4단계 추천 카드의 [알림 보내기]도 같은 문구·이력 흐름을 쓰므로, 그 개발이 끝난 뒤에 업체 연동 버튼을 붙이면 추천 카드에서도 바로 쓸 수 있다.

## 21. 실제 상품 분류 확인 결과와 규칙 종류(2026-11-23 — 2단계 구현 중 데이터 확인으로 설계를 보완)
- 실제 상품 분류는 의약품(drug)·사료(feed)·보조제(supplement)·조제·진료(service) 4가지뿐이고 **접종(vaccine) 분류가 없다.** 접종 상품은 "의약품" 안에 섞여 있다.
- 그래서 §12의 "분류로 접종(정보성)/재구매(광고 소지) 구분"과 §18의 `scale_by_quantity`는 **규칙의 종류(`kind`)** 로 바꾼다. `reminder_rules`는 `kind`('vaccine' 접종 안내 / 'rebuy' 재구매 안내)·`interval_days`·`lead_days`를 가진다(`scale_by_quantity` 열은 만들지 않는다).
  - **접종 안내(`vaccine`):** 정해진 간격(수량을 곱하지 않음), 정보성. 3단계 판매 화면의 "다음 접종: 3주 후/4주 후/1년 후" 버튼은 이 종류의 규칙이 있는 상품에만 나온다.
  - **재구매 안내(`rebuy`):** 판매 단위 1개당 일수 × 수량, 광고 소지(§12의 6개월 한도·(광고) 표기·야간 금지 적용).
  - **분류 규칙은 항상 재구매 안내**(DB에서 `vaccine` 종류를 막는다). 의약품은 종류가 많아 약(상품) 하나씩 정하는 것이 중심이다.
- 4단계 후보 계산은 상품 규칙(없으면 그 상품 분류의 규칙)의 `kind`로 접종/재구매를 구분한다.

## 22. 분류별 설정 삭제와 판매 화면에서 처음 정하기(사용자 결정, 2026-11-23 — 3단계)
- **분류별 주기 설정 화면은 없앤다.** 약·사료마다, 구매 개수마다 주기가 달라 큰 분류의 주기는 의미가 없다(사용자 지적). 알림 주기는 **약·상품 하나씩**만 정한다. DB의 분류 규칙 기능(`reminder_rules.group_name`)은 건드리지 않았고 화면만 뺐다.
- **판매 화면(관리자 전용):** 반려동물을 고르고 상품을 담으면 그 상품의 규칙이 있을 때 다음 알림일을 자동 계산해 보여 준다(재구매 = 1개당 일수 × 수량의 합계, 접종 = 정해진 간격). 날짜는 [날짜 고치기]로 바꿀 수 있고, 판매일을 바꾸면 자동 계산이 따라간다. 사장님이 직접 고친 날짜는 수량이 바뀌어도 유지된다. [알림 안 함]을 누르면 저장하지 않는다.
- **처음 정하기:** 규칙이 없는 상품이면 그 자리에서 "이 상품 1개로 며칠 쓰나요?"(7·14·30·60·90일·직접 입력)를 묻고, 누르면 그 상품의 규칙(재구매 안내)으로 저장되어 다음부터 자동으로 채워진다. 접종처럼 정해진 간격이면 3주·4주·1년 버튼(접종 안내)을 쓴다. 반려동물마다 다른 경우는 판매 때 날짜만 고친다(그 값은 그 반려동물에게만 적용).
- **`pet_next_due`:** (반려동물, 상품)당 한 행. 구매일(`sold_on`)을 함께 저장한다(설계의 `set_on` 대신) — 4단계에서 마지막 구매일보다 이른 구매 기준의 값을 무시하는 데 쓴다. 더 이른 구매일 기준의 저장은 더 최근 구매 기준의 기존 값을 덮어쓰지 않는다. 저장·삭제는 관리자 전용 함수 `rpc_set_next_due`(날짜가 비어 있으면 삭제)로만 한다.
- **판매 등록 함수(`rpc_create_sale`)는 바꾸지 않았다.** 다음 알림일은 판매가 성공한 뒤 따로 저장하며, 저장이 실패해도 판매 결과는 그대로이고 "다음 알림일 N건은 저장하지 못했어요" 안내만 덧붙는다.
- **수신 동의 체크박스(§16):** 반려동물을 고르면 그 보호자가 안내를 받기로 했는지 보이고 체크·해제로 저장한다(방법은 '구두', 날짜는 오늘). 문자를 원하지 않는 보호자는 체크가 잠기고 이유가 보인다.
- **내가 정한 것:** 이 기능은 관리자에게만 보인다(알림이 관리자 전용이고 직원 판매 화면의 위험을 줄이기 위해). 직원이 판매할 때 처음 정하기·수신 동의를 하려면 별도 결정이 필요하다. 계산 결과가 10년(3650일)을 넘으면 저장하지 않고 날짜를 직접 고르게 한다.
