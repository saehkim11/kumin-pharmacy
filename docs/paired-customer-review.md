# 사용자·개발자 쌍 검수 — 2026-11-14

## 진행 방식

기능 사용자와 개발자, 디자인 고객과 디자이너·개발자, 기획·공개 ERP 비교 고객과 ERP 개발자의 세 쌍으로 진행했습니다. 에이전트가 실제 이용자인 것처럼 사칭한 조사는 아닙니다. 사용자 역할이 Playwright에서 실제 화면을 조작하고, 개발자 역할이 불만을 접수해 재현·수정한 다음 원래 사용자 역할이 다시 확인하는 방식입니다.

검사 기준을 “메뉴가 열리고 오류가 없는가”에서 “사용자가 다음 화면에서 기대한 기록과 숫자를 실제로 찾을 수 있는가”로 확장했습니다. 실제 계정의 로그인·조회는 이용하되, 시험 등록·저장 요청은 브라우저 시험 응답으로 가로채 실제 업무 자료에 기록하지 않았습니다.

## 검증 구분

- PET-01·02: 사용자 역할이 지연 응답·조회 실패·빈 기록을 시험 응답으로 재현했습니다. 관리자·직원의 검색→상세 클릭으로 개발자 회귀 시험을 수행했습니다. 원고객 재검증에서 새 검색만 하는 경로와 진료 이력의 빈 안내를 추가 확인했습니다.
- D01·02: 1440·768·390·320px의 두 테마에서 기본 입력과 저장 버튼이 스크롤 없이 보이는지 확인했습니다. 선택 정보를 접어도 입력값이 제출되는지, 종류 선택이 유지되는지, 키보드로 펼칠 수 있는지도 검사했습니다.
- D03: 실제 상품 검색→선택→수량 10000→담기를 통해 `10,000` 표시와 판매·입고 숫자 정렬을 확인했습니다.
- PLAN-01·02: 실제 조회와 화면 클릭으로 과거 연도 누락을 확인하고, 시험 판매 응답 뒤 대시보드·분석 갱신을 비교했습니다. 개선 후 수치 비교와 자료 범위는 별도 분석 회귀 시험에 포함했습니다.

## 수정 후 원고객 재검증

- 디자인 고객은 원래 상품 담기·등록창 동선을 다시 실행해 D01~03을 수용했습니다. 390·320px에서 기본 등록창의 저장 버튼이 스크롤 없이 보이고, 선택 정보·닫기·날짜 아이콘의 어두운 모드 대비를 확인했습니다.
- 기획 고객은 판매 내역에서 과거 월을 조회한 뒤 분석에서 2024·2025·2026년과 엑셀 범위를 선택했습니다. 엑셀을 품목 기록 단위로 표시하는 설명을 확인했고, 시험 판매 뒤 새로고침 없이 분석 수익과 대시보드가 모두 기대값으로 바뀌어 PLAN-01·02를 수용했습니다.
- 기능 고객이 추가로 지적한 “B를 검색만 했는데 A 상세가 돌아옴”과 “진료 조회 실패를 빈 기록으로 읽을 수 있음”도 수정했습니다. 관리자·직원의 실제 검색·상세 선택으로 지연 응답·실패·성공 복원까지 회귀 시험했습니다.
- 통합 화면 검토에서는 데스크톱 상품 수익성 표의 마지막 열이 화면 밖에 가려지지 않도록 표를 세로 배치하고, 예보를 불러오는 안내가 날씨 한 칸에 세로로 잘리지 않도록 보완했습니다.

## 분석 자료 연결 규칙

- 자료 범위는 전체·판매 등록·엑셀 과거 판매로 선택합니다. 선택한 범위에 존재하는 과거 연도도 조회할 수 있습니다. 대시보드의 연결된 월별 그래프에도 현재 범위를 표시합니다.
- 엑셀의 영수증 번호를 만들지 않습니다. 등록 판매와 엑셀의 기록 번호는 별도로 구분하고, 엑셀 자료가 포함된 건당 지표는 주문이 아닌 품목 기록 기준임을 표시합니다.
- 엑셀은 원본 수익을 우선 사용합니다. 분석용 원가 금액은 매출액에서 이 수익을 뺀 값이므로, 원본 수익과 `수량 × 매입단가`가 맞지 않으면 원본 수익 기준으로 계산됩니다. 원본 수익이 없을 때만 매출액 − 수량 × 매입단가로 계산합니다.
- 매출액 또는 원가·수익을 확인할 수 없는 기록은 이익·원가·마진율 집계에서 제외하고 건수를 알립니다. 없는 원가를 0원으로 바꿔 이익을 부풀리지 않습니다.
- 판매·입고 저장 후 분석 자료를 다시 읽습니다. 읽기만 실패하면 저장 성공을 유지하고, 분석과 대시보드에 현재 수치가 이전 조회 기준일 수 있음을 표시합니다.

## 공개 ERP 비교에서 참고한 기준

외부 ERP의 개발자가 실제로 참여한 것은 아닙니다. 공개 소스와 공식 문서에서 보고서의 기간·자료 범위·판매액·원가·이익 구분 원칙을 검토했습니다. 새 프레임워크나 외부 코드를 이 프로젝트에 가져오지 않았습니다.

- [ERPNext 품목별 판매 보고서 소스](https://github.com/frappe/erpnext/blob/develop/erpnext/accounts/report/item_wise_sales_register/item_wise_sales_register.py): 기간과 품목별 판매 기록을 비교할 때 필터와 집계 대상을 일치시키는 기준으로 참고했습니다.
- [ERPNext 공식 이익 보고서 설명](https://docs.frappe.io/erpnext/gross-profit-report-differences): 서로 다른 장부·이익 보고서의 계산 범위가 다르면 숫자가 달라질 수 있으므로 자료 범위를 명확히 표시해야 한다는 점을 참고했습니다.
- [Odoo POS 결제 소스](https://github.com/odoo/odoo/blob/19.0/addons/point_of_sale/wizard/pos_payment.py): 결제 자료와 주문의 관계를 비교했습니다. 환불 같은 새 업무 기능을 이번 수정 범위에 임의로 추가하지 않았습니다.
